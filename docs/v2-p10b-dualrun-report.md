   `SONARLY_INGEST_INTERVAL_MINUTES=60`). Same volume mounts; v2 keeps the
   DB schema additive-compatible, so no DB export/import step exists.
3. **Boot.** The container runs v2's migrations (no-op baseline + nullable
   scan_jobs columns + FTS5 tables) and pushes one initial scan.
   Expect a reconciliation pass exactly like this report's: any file the old
   catalog claimed but that is not on disk is deactivated (v1 would do the
   same on its next scan).
4. **Verify.**
   `curl -fsS localhost:<port>/health` → 200; log in through the web UI;
   play one song start-to-finish in a Subsonic client; confirm
   `GET /api/scans/status` reaches completed with failed=0; eyeball the
   library counts against expectation.
5. **Done.** Keep the pre-v2 backup until v2 has soaked (recommend ≥1 week).

## Rollback procedure

1. Stop the v2 container.
2. Restore the DB: `cp -a config/sonarly/data.bak-pre-v2-*/sonarly.db* config/sonarly/data/`
   (main + -wal + -shm from the backup; SQLite replays the WAL on open).
   Any data written while v2 was live — scrobbles, ratings, new playlists —
   survives only if it predates the backup; state created after the backup
   is lost on rollback. Plan the soak window with that in mind (or take a
   fresh backup just before deciding to stay).
3. Swap the image/env back to v1 (`ghcr.io/miquelrosell99/sonarly:latest`,
   v1 env names) and start. v1 opens the restored DB with its own migrator.
4. Verify `GET /healthz` → 200, log in, play one song.

### Compatibility analysis (what v2 writes that v1 must tolerate)

Measured on this run, v2's only schema footprints over the v1 schema are:

- `schema_migrations` ledger rows (0001–0003) — a NEW table v1 never
  reads. Inert under v1.
- `scan_jobs.payload` and `scan_jobs.created_at` — **nullable** ADD
  COLUMNs (migration 0002). v1's scan_jobs inserts name explicit columns,
  so they succeed and the new columns stay NULL; v1's reads select its own
  columns. Inert.
- `songs_fts`/`albums_fts`/`artists_fts` FTS5 virtual tables
  (migration 0003) — new tables v1 never touches. Inert.
- Deactivation scoping delta (surfaced by the first, pre-rebase dual-run
  pass): v1's scanner deactivates every DB path not seen this scan except
  paths under a FAILED root; v2's scanner (`internal/modules/library`
  deactivateMissing) additionally skips paths under no walked library root —
  a deliberate hardening so a library-scoped scan cannot touch another
  library's rows. With the standard deployment (one library root, DB paths
  rooted under it) the behaviors are identical; the delta only surfaces
  when the DB holds paths outside every configured library root (e.g.
  after re-rooting the library without rewriting songs.file_path). In that
  situation v1 mass-deactivates the out-of-root catalog while v2 preserves
  it. Flagged here as a known, deliberate deviation — decide before cutover
  whether to port v1's behavior or accept the hardening.
- Re-persist normalizations observed on the 20 legacy rows this scan
  refreshed (all within the accepted parity envelope): `duration`
  fractional seconds -> integer seconds (SPEC-duration-integer-seconds,
  accepted by the P10 parity suite), legacy `" "`-valued `comment` /
  `music_brainz_id` -> NULL, and fractional legacy `bit_rate` -> NULL —
  the last because v2's pure-Go tag reader does not estimate a FLAC
  bitrate where music-metadata did. v1's current scanner would produce
  the same NULLs (its default persist is also full-replace); the
  duration/`bit_rate` response deltas only touch re-persisted legacy rows.

The baseline migration is pure `CREATE TABLE IF NOT EXISTS` over the exact
v1 001–049 shape, so no existing column/type/index is altered. Beyond
schema, v2 writes the same row shapes v1 writes (same tables, same column
semantics) — the catalog diff above shows the only content deltas are the
scan reconciliation (activity flags / provable moves / mtime+checksum
refreshes), which is ordinary v1-visible library state. No v2 row format is
unreadable to v1. (Claim grounded in the additive-migration design and
corroborated by this run's diff; the testparity suite proves the
request-level contract.)
